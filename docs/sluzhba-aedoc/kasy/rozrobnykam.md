# API для касового ПЗ (ПРРО / РРО)

Контракт каси **v2** — один для всіх способів підключення: онлайн до сервера обліку, клієнт каси (хмара), локальний режим. Каса, написана під нього, переходить між ними без змін — міняється лише адреса (і для сервера з мережі — токен).

## Підключення

| | Онлайн до сервера обліку | Клієнт каси (хмара) | Локальний режим |
|---|---|---|---|
| Адреса | `http://<сервер>:8766` або `http://127.0.0.1:8766` на сервері | `http://127.0.0.1:8766` | `http://127.0.0.1:8766` |
| Токен | з мережі — заголовок `X-Auth-Token` (обов'язковий); з `127.0.0.1` — без токена | без токена — лише з цього комп'ютера; якщо в клієнті задано токен — `X-Auth-Token` | так само, як клієнт каси |
| `source` у відповіді | `mirror` | `cloud` | `xtrace` |
| Видимість марок | усе сховище — свою точку вказує `point` | лише своя точка | лише свій об'єкт ЕО |
| `in_transit` | так | ні | так |
| `wrong_point` | так (якщо передано `point`) | ні | ні |
| `eoObjectCode` | код точки марки (`YJ0615C`) | код точки (`YJ0615C`) | UUID об'єкта ЕО |
| `productName` | порожньо | порожньо | назва товару з еАкциз |
| Папка `inbox` | на сервері (для каси на тому ж комп'ютері) | папка клієнта каси | папка служби |

- Формат — JSON, UTF-8; `Content-Type: application/json` для запитів з тілом.
- Дата й час — `yyyy-MM-ddTHH:mm:ss`, місцевий час, без часового поясу.
- Ідентифікатор марки — з урахуванням регістру, в адресі — URL-кодований. Рекомендований тайм-аут — 2–3 с.

## Головне правило

Каса завжди передає пару **акцизна марка + штрихкод товару** (`barcode`). Відповідь — один підсумок:

- `ok: true` — марку можна продавати з цим товаром;
- `ok: false` — не можна: `error` — код для програми, `message` — текст для касира.

Решта полів — довідкові. Служба **нічого не забороняє** сама: що робити при `ok: false`, `stale: true` чи недоступному сервісі — вирішує каса.

| `error` | Коли | Порядок перевірки |
|---|---|---|
| `barcode_required` | каса не передала штрихкод товару | 1 |
| `not_found` | марки немає в залишку; на сервері обліку — ще й марка не на складі (`message`: «марка не на складі: ВідвантаженоКонтрагенту») | 2 |
| `wrong_point` | каса передала `point`, а марка іншої торгової точки (лише онлайн до сервера) | 3 |
| `already_sold` | марку вже продано (тут чи на іншій касі; на сервері — ще й статус `Порушення` / `ПроданоПозаОбліком`) | 4 |
| `in_transit` | марка «В дорозі» — її треба прийняти в еАкциз | 5 |
| `barcode_unknown` | для марки немає штрихкоду товару — перевірити неможливо | 6 |
| `barcode_mismatch` | марка від іншого товару (напр. марка з горілки на пачці сигарет) | 7 |

Штрихкоди порівнюються лише цифрами без ведучих нулів: EAN-13, UPC-A і GTIN-14 одного товару збігаються.

**Статуси сховища (сервер обліку) → відповідь:** `НаСкладі` — перевірка штрихкоду; `Вдорозі`, `ВдорозіПереміщення` — `in_transit`; `ПогашеноЕМ`, `Порушення`, `ПроданоПозаОбліком` — `already_sold` (з даними першого продажу, якщо є); решта (`ВідвантаженоКонтрагенту`, `ВдорозіКонтрагенту`, `МиВідхилено`, …) — `not_found` зі статусом у `message`.

### Точка каси `point`

Онлайн-каса бачить усе сховище, а не лише свою точку. Необов'язковий параметр `point` — код точки каси (`YJ0615C` = код ЕО + код об'єкта): у `GET` (`?point=`), у тілі `batch` (загальний або в елементі), у тілі `/sold`, у файлі `inbox`. Задано і марка іншої точки → `ok: false`, `error: wrong_point` («марка іншої торгової точки: …»). Не задано — не перевіряється.

## Коли що викликати

| Момент | Виклик | Що робити з відповіддю |
|---|---|---|
| Скан товару і марки | `GET /marks/{id}?barcode=…` | `ok` — додати в чек; інакше показати `message` |
| Перед оплатою | `POST /marks/batch` | перевірити всі пари чека одним запитом; `ok` верхнього рівня — усі пари `ok` |
| Після фіскалізації | файл у `inbox` (якщо каса на тому ж комп'ютері) або `POST /marks/{id}/sold` | продаж записано завжди (`recorded: true`); `ok: false` — продано проблемну марку, розбір — в обліковій системі |

Поля стану в кожній відповіді `GET` / `batch`:

- `stale: true` — залишок може бути неактуальним (немає зв'язку довше `StaleMinutes`, облікова система давно не оновлювала дані, сховище заморожене); на `ok` не впливає;
- `frozen: true` — сховище заморожене (майстер міграції); продажі приймаються;
- `cloudError` — текст для адміністратора (відмова за правами, токен еАкциз закінчується); інакше порожньо.

## `GET /marks/{id}?barcode=…[&point=…]`

Завжди 200 (400 — лише для некоректного запиту, 401 — невірний токен):

```json
{"uniqueIdentifier":"T25…","barcode":"6412700021027","ok":false,"error":"barcode_mismatch",
 "message":"марка від іншого товару: Віскі США Джек Деніелс, 1л (штрихкод 5099873045367), відскановано 6412700021027",
 "found":true,"inStock":true,"status":"НаСкладі","bc":"5099873045367","productName":"Віскі США Джек Деніелс, 1л",
 "eoObjectCode":"YJ0615C","updatedAt":"2026-10-18T12:00:00",
 "sold":false,"soldAt":null,"soldHere":false,"receiptFn":null,"rroFn":null,
 "stale":false,"frozen":false,"cloudError":"","source":"cloud"}
```

- `ok: true` — `error` і `message` порожні;
- `bc` — штрихкод товару марки (порожньо — невідомий); `status` — `НаСкладі` / `Вдорозі` / `ПогашеноЕМ`, на сервері — фактичний статус сховища;
- продана: `sold: true`, `soldAt`, `receiptFn`, `rroFn`, `soldHere` — на цій касі чи на іншій.

## `POST /marks/batch`

Тіло — до 500 пар:

```json
{"point":"YJ0615C","items":[{"id":"T25…","barcode":"6412700021027"},{"id":"T25…","barcode":"5099873045367"}]}
```

Відповідь `{"ok":false,"items":[…кожен як GET…],"stale":…,"frozen":…,"cloudError":…}`; `ok` — усі пари `ok`; порядок елементів — як у запиті. Елемент без `id` або тіло без `items` — 400.

## `POST /marks/{id}/sold`

Викликати **після** фіскалізації чека. Тіло:

```json
{"receiptFn":"<фіскальний номер чека>","rroFn":"<фіскальний номер РРО/ПРРО>","barcode":"<штрихкод товару>",
 "soldAt":"yyyy-MM-ddTHH:mm:ss","cashRegister":"<назва каси>","point":"<код точки, необов'язково>"}
```

`receiptFn`, `rroFn`, `barcode` — обов'язкові. `soldAt` — якщо немає, береться поточний час. `cashRegister` — якщо немає, з налаштувань.

| Код | Коли | Тіло |
|---|---|---|
| 200 | продаж записано (і повтор того ж чека — `duplicate: true`) | `{"recorded":true,"ok":…,"error":…,"message":…,"status":"ПогашеноЕМ","soldAt":…}` |
| 400 | немає `receiptFn` / `rroFn` / `barcode`, поганий `soldAt` | `{"error":"bad_request","message":…}` — **не записано** |

`ok` / `error` — чи можна було продавати цю марку з цим товаром (стан до продажу; повтор того ж чека не вважається `already_sold`). Для `already_sold` — ще `firstSale` (`receiptFn`, `rroFn`, `soldAt`, `soldHere`) — дані **першого** продажу.

Після обриву зв'язку надішліть `/sold` ще раз — повтор того ж чека не створює дубля (`duplicate: true`).

**Сервер обліку:** продаж записується в сховище й передається обліковій системі; розбіжності — у протокол обміну облікової системи: другий продаж іншим чеком — `already_sold` (не проводиться), марка іншої точки — `wrong_point` (проводиться з позначкою), марка не на складі чи її немає — `not_found`. Сховище заморожене (майстер міграції) — продаж приймається в чергу: `"queued": true`, `message` «продаж прийнято, проведеться після завершення міграції».

## Папка `inbox`

Для каси на тому ж комп'ютері, що й клієнт каси / служба (на сервері обліку — **«Папка inbox»** у налаштуваннях); віддаленим касам — `/sold`. Один файл на чек: `inbox\<rroFn>-<receiptFn>.json`

```json
{"receiptFn":"3000123456","rroFn":"4000000001","soldAt":"2026-10-19T12:30:00","cashRegister":"Каса 1","type":"sale","point":"YJ0615C",
 "marks":[{"id":"T25VGXZC1FGNYJ065pWys","barcode":"6412700021027"},{"id":"T25VGXZNBCWRYJ065pWys","barcode":"5099873045367"}]}
```

- писати спершу у `…json.tmp`, потім перейменувати в `.json` — береться лише `*.json`;
- `type`: `sale` (за замовчуванням) або `return` (повернення — поки лише записується в журнал);
- кожна марка — `{"id","barcode"}`, штрихкод обов'язковий; обробляється як `/sold`; `point` — необов'язковий;
- результат: файл переноситься в `inbox\done\` і поруч з'являється `<ім'я>.result.json` (відповідь по кожній марці: `code`, `ok`, `error`, `message`);
- помилка (немає `receiptFn` / `rroFn` / марок / штрихкоду, поганий JSON) — `inbox\error\` + `<ім'я>.error.txt` з причиною, **жодна марка файлу не записується**;
- файли, покладені, поки служба не працювала, обробляються під час старту; повторний файл з тим самим чеком не створює дублів.

## Перевірка

Обробка **«AEDOC: тест каси»** (надає підтримка): адреса, токен `X-Auth-Token`, точка `point`, ручна перевірка чека й автотест.

!!! warning "Старий API (до версії служби 1.0.5)"
    Попередній варіант API (лише ідентифікатор марки, `ids` у batch, `receiptRef`, коди 404 / 409 / 503) прибрано. Касові програми під нього треба перевести на контракт v2: пара «марка + штрихкод товару», підсумок `ok` / `error` / `message`, `receiptFn` + `rroFn` + `barcode` у продажі.
